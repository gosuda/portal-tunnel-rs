# R10 threat mapping — v0.1

This template is consumed at release-tag time by the U8.10 release-engineering
pipeline (`cargo release` post-tag hook injects it into the GitHub release
body). It maps each R10 threat class (a-h) — sourced verbatim from
[`docs/threat-model.md`](../threat-model.md) §"R10 threat classes (a-h)" —
to its v0.1 mitigation posture and the trigger criterion that promotes the
matching v0.2 backlog work to active.

The honest line: v0.1 ships **per-relay defenses**. Cross-relay coordination
(`ReputationDelta` propagation, shared blocklists, registry quorum, operator
mesh) is v0.2 work behind explicit triggers — see `PLAN.md` §"v0.2 Backlog".

## How to read the status column

- **mitigated by single-relay defense** — v0.1 ships a complete defense
  scoped to the relay's own observation window. No cross-relay coordination
  is required for the defense to be load-bearing.
- **partially mitigated** — v0.1 has a defense but its effectiveness depends
  on data the relay may not always have (e.g., ASN metadata) or on attack
  shapes the per-relay scope cannot fully observe (e.g., legitimate traffic
  spread across operators that aggregates to a rate-limit-violation
  threshold).
- **unmitigated in v0.1 (cross-relay required)** — v0.1 ships the wire
  reservation (envelope, domain separator, size budget) and the no-emit CI
  gate, but no defense activates until cross-relay propagation lands in v0.2.

## v0.2 backlog promotion procedure

The v0.2 Trigger column lists the falsifiable observable that promotes the
matching v0.2 backlog item from "deferred" to "active work". Per `PLAN.md`
§"Decision Stability — v0.2 Backlog freeze trigger", a v0.2 item is
re-evaluated only when its trigger fires; until then, the v0.1 posture
above is the shipping posture.
