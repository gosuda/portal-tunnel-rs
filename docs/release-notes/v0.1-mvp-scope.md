# portal-tunnel-rs v0.1 — MVP scope

> **This file is a template.** It is checked in pre-tag with the structure
> below; at v0.1 tag time the U8.10 release-engineering pipeline editor
> reviews each row, moves items between sections to match the actual tag
> commit's state, and the result lands as the GitHub release body via the
> `cargo release` post-tag hook. Forecasts belong in [`PLAN.md`](../../PLAN.md);
> this document records facts at tag time.
>
> Pre-tag, every "Ships in v0.1" entry below is a candidate that is verified
> against the tag commit before the release fires. Reviewers move any
> candidate that did not actually land into "Deferred to point release or
> v0.2" with an explicit reason.

The honest line: v0.1 is a **greenfield Rust port of `gosuda/portal-tunnel`
v2.1.8** with no wire-level interoperability with Go deployments (per
ADR-0001) and no kernel WireGuard requirement (per ADR-0014).

## Ship candidates

> **Pre-tag wording.** At v0.1 tag time the editor renames this section to
> "Ships in v0.1" and verifies each candidate against the tag commit before
> the release body is published. Any candidate that does not appear in the
> tag commit is moved to "Deferred to point release or v0.2" with a reason.

Each entry below is a candidate for v0.1 tag. The pre-tag editor confirms it
against the actual repo state and either keeps it (rename + ship) or moves
it to Deferred.

### Phase 0 — Foundation (R7-R9)

- Workspace governance: `Cargo.toml` workspace-deps register,
  `rust-toolchain.toml` pinning Rust 1.95, ADRs 0001-0005 + 0014 + 0015,
  `AGENTS.md` constitution, `deny.toml` ban list, `prek.toml` git hooks,
  `.cargo/config.toml`, `.github/workflows/ci.yml` gates, nine crate stubs.

### Phase 1 — Wire (R1-R6, SEC-001..007)

- `crates/portal-wire/` greenfield wire types, codecs, framing
  (`Channel::{Control, TcpProxy, UdpDatagram, HopRoute}`), envelope claim
  set (`SEC-001`), domain separators (`SEC-007`).
- [`docs/wire-protocol.md`](../wire-protocol.md) — single source of truth
  for the on-the-wire bytes.
- [`docs/threat-model.md`](../threat-model.md) — adversary capabilities,
  multi-hop privacy claim, R10 8-class enumeration.
- U16 drift gate (`xtask wire-drift-check` + v0.1 `ReputationDelta`
  no-emit grep) and U17 proptest suites at `PROPTEST_CASES=4096`.

### Phase 2 — Crypto (R2, SEC-001..003)

- `crates/portal-crypto/` two-key tenant identity
  (`SecretBox<TenantSecp256k1Key>` + `SecretBox<RelayEd25519Key>`); per-role
  load functions enforced by clippy `disallowed-methods`
  (`load_all_keys` ban) plus the multi-key-return regex gate.
- SIWE wrapper + SIWE-to-ed25519 binding (`SEC-002`).
- ENS resolution via `alloy`.
- Domain-separated `sign_with_separator` API (`SEC-007`).

### Phase 3 — Transport (R5, R12)

- `crates/portal-net/` QUIC backhaul via `quinn 0.11` + `aws-lc-rs` rustls
  provider; ALPN `portal/2`; SPKI-pin verifier; dual-stack v4+v6 listeners
  with v4-mapped-v6 canonicalization (R12).
- TCP port relay + UDP datagram session.
- SDK-side stream/datagram client.
- `PortAllocator` with grace-period reservation.

### Phase 4 — ACME (R13)

- `crates/portal-acme/` `DnsProvider` trait + per-role
  `SecretBox`-wrapped credential newtypes.
- Local self-signed dev provider (`rcgen` ECDSA P-256, 10y, SAN, 0o600).
- Cloudflare DNS-01 provider via `cloudflare = 0.14` + wiremock contract
  test.
- `instant-acme 0.8` ACME client.
- `Manager` lifecycle + maintenance loop (local mode).

### Phase 5 — Relay (R2, R12, SEC-004..005, partial R10 v0.1)

- `crates/portal-relay/` lease registry (`papaya 0.2` `pin_owned()`);
  per-relay policy runtime (`governor` rate limiting + IP filter +
  `ProxyTrust` R12 canonicalization); admin/SDK/discovery API surfaces;
  ECH router; server orchestrator with lease janitor.
- `cargo-vet` supply-chain audit harness.

### Phase 6a — SDK (R10 v0.1 picker, SEC-013)

- `crates/portal-sdk/` expose orchestration + listener accept loop
  scaffolds; `TunnelEvent` broadcast bus consumed by `portal-cli`'s R15 TUI.
- Eclipse-resistant relay-set picker (≥3 ASN bins when ASN data is
  present; honest degradation with operator override otherwise).
- RFC 5705 EKM-based MITM probe primitive (`derive_probe_ekm`).

### Phase 6b/B — Overlay decision artifacts

- ADR-0014 (overlay architecture: sealed `WgDevice` + smoltcp +
  QUIC-on-smoltcp-UDP hop-mux).
- ADR-0015 (WG userspace fork pick: `defguard_boringtun 0.6.5` primary;
  NepTUN secondary pending license review).
- Workspace dep declared (`defguard_boringtun = "0.6.5"`).

### Phase 7 — Binaries + behavioral gates

- `portal-relay-bin` (binary `portal-relay`) with embedded React admin SPA
  + SvelteKit docs bundle (per R14 v0.1 frontend strategy).
- `portal-cli` (binary `portal`) + `portal-demo` minimal surfaces.
- Behavioral gates: dep-spawning audit (U8.7 / `xtask dep-audit`), utoipa
  coverage gate (U8.8 / clippy `disallowed-methods` + ast-grep), R10
  threat-class mapping ([`v0.1-r10-threat-mapping.md`](v0.1-r10-threat-mapping.md)).

## Conditional — fork-pick cliff outcome (Phase 6b/B)

ADR-0015 names a 2026-08-04 go/no-go date for the userspace WG fork pick.
At v0.1 tag time, exactly one of the two outcomes below applies; the
pre-tag editor selects which branch ran and deletes the other.

- **If the cliff cleared:** v0.1 includes
  `crates/portal-relay/src/overlay/` with the `WgDevice` adapter (Phase 6b/B U6),
  smoltcp netstack (Phase 6b/B U7), and the `quinn::AsyncUdpSocket`
  bridge documented in ADR-0014. Multi-hop overlay routing is operative.
- **If both forks integration-blocked (MVP-without-overlay):** v0.1
  ships single-hop relay backhaul only. The `crates/portal-relay/src/overlay/`
  module is empty or absent. Multi-hop defers to v0.2 per F11.
  Vendoring `wireguard-go` is **not** a v0.1 fallback (3-6 month
  rewrite per F11).

re-evaluated only when its trigger fires.

| Item | Trigger criterion |
|---|---|
| **R10 cross-relay propagation** (`ReputationDelta` envelope wire path) | v0.1 ships AND ≥1 operator with >2 relays reports false-positive rate-limiting at single-relay scope |
| **R11 `tokio-console` + admin dashboard** | v0.1 ships AND a production incident is attributed to lack of async runtime visibility |
| **R13 server-side ECH** on relay HTTPS | rustls#1980 PR lands upstream |
| **R14 Leptos-native admin UI + mdbook docs** | v0.1 ships AND Node toolchain dependency causes a CI failure OR a named external contributor requests UI changes |
| **R15 admin/launch/config TUI views** | v0.1 ships AND ≥3 operators cite missing TUI functionality as blocking |
| **Performance benchmarks vs Go v2.1.8** | v0.1 ships |
| **Full `utoipa` snapshot CI gate** (xtask openapi-export → docs/openapi.yaml + diff CI) | v0.1 ships |

## Behavioral gates that established the ship

The following gates ran on every PR into v0.1 and must be green at the v0.1
tag commit:

- **Wire drift gate** ([U16](../plans/2026-05-04-001-feat-portal-wire-plan.md))
  — `cargo xtask wire-drift-check` confirms `docs/wire-protocol.md`
  source-SHA marker matches `git log -1 --format=%H -- crates/portal-wire`.
- **`ReputationDelta` no-emit gate** — CI grep over v0.1 runtime crates;
  R10 v0.2 ships the type, v0.1 emits zero.
- **Wire proptest suites** ([U17](../plans/2026-05-04-001-feat-portal-wire-plan.md))
  — five named `proptest_*.rs` suites at `PROPTEST_CASES=4096` on CI.
- **Dep-spawning audit** ([U8.7](dep-spawning-audit.md)) — `cargo xtask
  dep-audit` confirms every required dep contract section is present;
  validator rejects fenced-code-block and blockquote bypasses.
- **utoipa coverage gate** ([U8.8](../utoipa-coverage-policy.md)) —
  clippy `disallowed-methods` plus ast-grep belt-and-suspenders on the
  chained-builder syntactic shape.
- **R2 trust-boundary gate** — clippy `disallowed-methods`
  (`portal_crypto::load_all_keys`) plus the multi-key-return regex CI step.
- **rustls-MANDATORY gate** — `cargo tree -i openssl` returns empty.
- **e2e harness** (Phase 7 Batch 3) and **behavioral-trace harness**
  (Phase 7 Batch 4) — required green before v0.1 tag.

## Migration posture from Go v2.1.8

ADR-0003 ([`registry-fork-and-v2-1-8-migration.md`](../adr/0003-registry-fork-and-v2-1-8-migration.md))
is the canonical statement of the v2.1.8 user-base migration posture.
Summary:

- Greenfield wire (per ADR-0001) means **no byte-level interoperability**
  between v0.1 Rust and v2.1.8 Go deployments.
- Existing v2.1.8 deployments are not auto-upgraded; operators choose to
  migrate at a clean cutover point.
- Parallel maintenance posture: v2.1.8 Go and v0.1 Rust ship side-by-side;
  registry-fork strategy ensures both populations have authoritative
  registries.
- ADR-0004 ([`supported-clients-and-upgrade-encouragement.md`](../adr/0004-supported-clients-and-upgrade-encouragement.md))
  bounds what greenfield removes for the public-internet client base.
